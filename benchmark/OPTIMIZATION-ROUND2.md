# 第二轮优化报告

日期：2026-10-10（Asia/Taipei）。本轮基线为第一轮全部优化完成后的构建，保存在 `benchmark/baseline-round2/dist/`。

## 已保留的改动

1. 匹配查找缓存当前位置的四字节前缀，并复用它计算哈希。已有最佳匹配时先检查候选尾部，排除不能更长的候选；通过检查后仍扫描中间内容。保持哈希、候选访问顺序、最长匹配与距离选择不变。
2. `prev` 改为 32768 个槽位的环形链表，保存绝对位置，只在读取/写入槽位时取窗口掩码。始终先搜索当前位置，再插入复用的槽位；lazy 前瞻和批量插入沿用原来的顺序。
3. Brute 过滤改用精确的 raw DEFLATE 位数计数，共用真实编码器的匹配、token、频率和选块逻辑。计数包含块头、额外位、结束码和 stored 块的实际字节对齐，按当前最佳尺寸熔断，省去压缩输出缓冲、编码表构造和逐 token 位写入。尺寸相等时仍拒绝后来的过滤器，保留原有排序。

直接让 Brute 生成有尺寸上限的压缩流，初测慢约 3%；改为轻量错误返回仍慢约 3%，这两版已撤回。最终采用精确计数方案，过滤字节与过滤器选择均保持一致。计数入口仅供内部试验使用，没有加入包的公共导出；公共 raw/zlib API 的错误类型和行为保持不变。

## 内存

`prev` 容量从输入长度 × 4 字节变为固定 128 KiB。例如 1024×1024 RGBA 图的带过滤数据长 4195328 字节，旧链表需要 16781312 字节（约 16 MiB），新链表需要 131072 字节，减少约 15.9 MiB。这是链表容量计算，不是整个程序的峰值内存测量；解码与过滤输出仍按图片大小分配。

Brute 的计数路径不再为每个候选分配原来约输入长度一半的输出缓冲，结果只返回长度。

## 验证

- `bun run build` 与 `bun run typecheck`：通过，dist 和浏览器站点 bundle 均已更新。
- `bun run test`：438/438，10 个测试文件。
- 390 组 raw/zlib 对比：全部 0–12 编码级别均与本轮基线逐字节一致，并通过 Node zlib 独立解压。覆盖非零 byteOffset、窗口边界、跨块与后段不匹配数据。
- 20 组 Brute 过滤/透明像素试验：过滤字节与过滤器选择完全一致，原始像素缓冲保持不变。
- 新增测试还覆盖 32767/32768/32769 字节距离的基线输出指纹、精确计数与真实输出的尺寸上限、compressed→stored 块的字节对齐、Brute 的滚动窗口/重置/严格排序及异常传播。

最终真实图片 benchmark 使用独立 pngjs 解码比较输入与输出，并强制基线与当前构建逐字节一致。计时在验证结束后单独运行，交替测量两个构建，1 次 warmup，3 次测量取中位数；总耗时是每张图片中位数的总和。四个样本的结果不能代表所有 PNG 或硬件。
